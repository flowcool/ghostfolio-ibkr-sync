# Spec Delta

## MODIFIED Requirements

### Requirement: Exact replacement and reference preservation

A manually approved financial update SHALL replace the displayed activity fields with the validated current IBKR conversion. A profile-authorized financial update SHALL replace only fields allowed by activity-reconciliation. A reference-only update SHALL replace only the connector comment and preserve every other field. The full proposed comment SHALL be visible before approval. Keep the destination activity ID, destination account, owner and tags. Do not delete or create an activity for a correction. Preserve non-reference user text and all other destination fields outside the explicitly approved changes. Dates/scaling/fee clamps SHALL use the normal import conversion; diagnostic tolerance SHALL grant no write authority.

Define proposed numbers from the exact JSON payload that the current conversion and qualified serializer will send. Show that value as plain-decimal text without additional report rounding. Parse destination response bytes as exact decimals in live and simulated review. Compare numeric values exactly: `1`, `1.0` and `1e0` are equal; financial tolerances SHALL NOT apply. Do not reconstruct destination evidence from already decoded floats. Refuse non-finite values, transport overflow/underflow or loss of any preserved numeric value. A repeating source quotient is represented by the existing conversion's transmitted value, not by an invented exact rational payload.

Compare source and destination dates by their calendar day in configured `TZ`, after qualified Flex conversion to UTC. Equivalent offsets and fractional-second spellings remain compatible. Different instants on the same local day SHALL be date-compatible: emit no date proposal and preserve the stored date, including during other approved field updates. This intraday difference SHALL NOT exclude comment-only identity migration when all other checks pass. A different local day SHALL be a real date difference and require the existing reviewed correction path. Conservative and balanced profiles require the same local day; permissive retains its inclusive two-day BUY/SELL and three-day DIVIDEND limits. Proposed trade times, dividend days and corporate-action timestamps SHALL use this conversion. UTC calendar dates SHALL control baseline manual proximity; active profile eligibility SHALL use the configured local calendar under activity-reconciliation. Missing, unknown or unsupported source timezone evidence SHALL make exact correction non-actionable. A reference-only identity migration SHALL preserve the stored date; it SHALL not silently repair a date. Stored dates SHALL be repaired only through the existing reviewed financial correction path, with manual `yes` or profile authority where allowed, backup, durable journal and exact readback. Normal sync SHALL NOT rewrite them. Such a repair requires a separate operation step and operator GO after release. No new conversion tool is part of this change.

The canonical v2 reference SHALL occupy the first comment line. If user text exists, append one blank line and that preserved text. Recognized historical references SHALL be removed only when the entire comment is exactly the proven legacy `IBKR#<tradeID>` or `dividend#<key>#<date>` marker. Validate the identifier/key/date against the source and existing supported format; exclude reserved versioned forms from the legacy trade grammar. Canonical v2 supports either the whole comment or the first line followed by exactly one blank separator line and preserved notes. Legacy aggregates that require splitting or merging remain excluded. Several activities sharing a legacy dividend alias can migrate separately only when activity-reconciliation proves mutually unique one-to-one pairs. Text that merely mentions a reference SHALL remain user text. Ambiguous, multiple or malformed reserved references SHALL be refused, not guessed. No comment truncation SHALL be allowed. If API trimming, length or encoding prevents preserving the proposed comment, keep the proposal non-actionable with the reason.

All readers SHALL extract the reference from that first line without treating user text as identity. The original whole-comment v2 forms and legacy readers SHALL remain compatible. Unknown reserved versions and invalid identity segments SHALL still stop before writes. Identity comparison SHALL use the extracted marker, not the full notes-bearing comment. This behavior SHALL remain available when review is later disabled.

#### Scenario: Full correction and preserved metadata
- **WHEN** `python -m pytest -q tests/test_activity_review.py -k review_replacement` covers BUY, SELL, DIVIDEND, fractional amounts, supported minor-unit denominations, every changed field, qualified EST/EDT timestamps, compatible intraday times, different local days and corrected UTC dates
- **THEN** only the approved replacement fields change, the review shows source text and both date contexts, exact readback proves every approved change and preserves the stored instant for date-compatible rows, and no POST/DELETE, report rounding or automatic historical repair occurs. Include repeating dividend quotients, exact wire decimals, equivalent numeric/date spellings and unpreservable transport values; representation changes alone do not fail readback.

#### Scenario: Legacy intraday date compatibility
- **WHEN** the stored date is `2026-01-19T07:03:00Z`, the corrected source date is `2026-01-19T00:00:00Z`, configured `TZ` is `Europe/Paris`, and all other migration checks pass
- **THEN** both dates have local day `2026-01-19`, no date proposal is emitted, comment-only migration is eligible, and its exact readback preserves `2026-01-19T07:03:00Z`.

#### Scenario: Reference upgrade and user notes
- **WHEN** `python -m pytest -q tests/test_activity_review.py -k review_reference` covers manual notes, every recognized legacy form, v2 with notes, reference-like prose, Unicode text, boundary lengths, trimming, malformed/duplicate markers and a date mismatch
- **THEN** exact old references are replaced only when date evidence is eligible, notes survive, all readers deduplicate the canonical first-line identity, v2 identity remains stable, and unsupported comments or an ineligible date remain visible without a PUT.
