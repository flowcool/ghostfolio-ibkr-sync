# Activity correction review delta

## MODIFIED Requirements

### Requirement: Optional persistent review file

`ACTIVITY_REVIEW_FILE` SHALL enable review only when its ENV value is nonblank. The path SHALL name a regular YAML file in a persistent writable directory. A missing file SHALL be created after valid input acquisition. A missing parent, unreadable existing file, invalid schema or unsafe path SHALL NOT be treated as an empty review. No existing file SHALL be cleared as recovery from a parse error.

When disabled, the connector SHALL create no review file or journal and send no correction requests. Existing import selection, cash handling and diagnostic behavior SHALL remain unchanged. Identity reading SHALL still support comments produced by an earlier enabled run.

The review SHALL publish compact schema 3 as one operator YAML. It SHALL contain a summary, keyed groups, keyed `reference_updates` and keyed `activity_corrections`. The first proposal section SHALL contain comment-only operations. Derive the section from rebuilt operation fields. Show stable key, evidence revision, source event, destination activity, readable security/type, execution path, match evidence, profile authority, status, relevant current/proposed fields and `decision`. Association evidence SHALL distinguish recognized v2 identity, legacy alias, manual proximity and profile match. Blocking SHALL be a separate status, not a replacement for association evidence. No confidence label SHALL authorize a request.

Show full current/proposed connector comments and every exact changed value. Show observed differences even when execution is blocked. Keep diagnostic differences separate from operation fields, so a comment-only migration never approves the remaining date or financial changes. Retain exact common values needed for a decision, normalized gross, separate fees and date context. Do not repeat full account, platform, asset metadata or snapshots in each operator entry. Store complete exact evidence in private internal state. Values SHALL be plain English and exact decimal text. Formatted totals SHALL NOT replace exact changed values.

The summary SHALL distinguish unique source events, destination activities and candidate counts. Include actual outcomes, selected profile and simulation status. Show conforming activities as compact counts with keyed drill-down records in this same file. Group records SHALL name their member keys and distinct totals. Each blocked record SHALL name conflicting activity/event IDs, observed evidence or missing proof, held scope and a concrete action. Do not invent a conflict counterparty when none is known. Do not generate HTML or require another operator decision file.

Schemas 1/2 SHALL remain readable. Import their full evidence, clear approvals once and publish schema 3. Never manufacture a rejection from a legacy non-yes value. Keep pending journal formats and fences readable. Old readers SHALL refuse schema 3. Missing or mismatched internal state SHALL NOT be interpreted as empty. Missing state is allowed only during first initialization from valid fresh inputs or an intact legacy file. Unknown keys, invalid bindings and duplicate YAML keys SHALL remain errors. Exclude credentials.

- **THEN** old approvals clear once, journals remain recoverable, blocked differences and group causes stay visible, exact proposed comments remain readable and metadata duplication leaves the operator view.


### Requirement: Source events and candidate selection

Review SHALL cover supported BUY, SELL and DIVIDEND events. A trade SHALL be one source-account/tradeID event. A dividend SHALL be one source-account/actionID event after the complete existing cash, withholding and quantity validations. Several cash portions of that same action SHALL retain the current proven conversion. Separate fills or actions SHALL NOT be combined to fit one destination activity. Invalid, conflicting, zero/negative-net, incomplete or future source events SHALL NOT become writable proposals.

An exact recognized v2 reference SHALL select its event before proximity. A current reference with different values SHALL still produce a proposal. A unique exact current reference with expected values SHALL produce no correction or PUT and SHALL follow activity-reconciliation conformity reporting. A legacy alias SHALL not claim exact per-event identity when several source actions share it. Eligible legacy references SHALL produce independent comment-only migration proposals under activity-reconciliation. Runtime migration SHALL trust the explicit account mapping and refuse observed conflicts; absence of historical cross-account coverage alone SHALL NOT block it. Acquire and validate all configured reports before dispatch, then reuse that inventory. Invalid evidence for a relevant source or detected cross-account collision SHALL block the affected operation; unrelated valid accounts SHALL continue. Historical maintenance remains a separate path with its existing proof and operation authorization.

Without an exact recognized reference, candidates SHALL have the same verified destination account, BUY/SELL/DIVIDEND type, resolved security and supported denomination. A nonempty conflicting ISIN SHALL exclude a candidate. Active YAHOO/account requirements SHALL remain. A row with another source event's recognized reference SHALL NOT become a proximity candidate.

With reconciliation off, manual discovery SHALL retain inclusive two-day BUY/SELL and three-day DIVIDEND UTC windows and exact-reference precedence. With a profile active, automatic eligibility SHALL use activity-reconciliation local-calendar windows, gross thresholds and quantity rules. Build the visible candidate set from the union of manual discovery and the active profile search so UTC edges cannot omit a valid local-day profile candidate. Financial thresholds SHALL NOT hide manual candidates. Candidate order and keys SHALL be deterministic. Several candidates SHALL remain visible. Automatic authority SHALL require the complete mutual-uniqueness check; confidence or amount agreement alone SHALL NOT authorize writes.

### Requirement: Approval and one-to-one conflicts

Only the literal lowercase scalar `yes` in `decision` SHALL give manual consent for a displayed operation, whether plain or quoted. Literal lowercase `reject` SHALL reject only that source-target association under Pending proposals and file refresh. Null SHALL remain pending. Other tokens SHALL skip with a warning and SHALL NOT establish consent or rejection. Distinguish `yes` from boolean `true`; generic YAML truthiness SHALL NOT authorize writes. Unknown fields and invalid bindings SHALL remain errors. An active reconciliation profile SHALL provide separate automatic authority only within its own contract. An explicit valid rejection SHALL take precedence over that authority.

The operator SHALL edit only `decision`. Editing another proposal field SHALL NOT turn it into a replacement input: fresh evidence SHALL reconstruct the expected proposal and clear any invalid approval. A proposal generated during the current run SHALL start blank. Only an unchanged actionable proposal already manually approved when the run read the file SHALL be eligible for manual dispatch. An automatic proposal can dispatch during discovery only after independent fresh profile evaluation. Bind manual consent to source evidence, exact operation fields, target account/owner, tags, notes, mapping, identity occupancy, execution path and actionability. Changes to those inputs SHALL clear approval. Profile-derived evidence labels, authority, eligibility, policy version and TZ alone SHALL NOT enter that manual binding or evidence revision. A profile or TZ change alone SHALL NOT clear manual consent for an unchanged operation. A blocked proposal SHALL never execute, including when it contains yes.

Manual and automatic selections together SHALL form a one-to-one set across the complete review, including staged historical selections. More than one approved destination for one source event, or more than one approved event for one destination, SHALL refuse every conflicting correction before dispatch. Unselected candidates SHALL remain pending until a selected correction is confirmed; they SHALL NOT be silently selected or deleted as duplicates.

- **THEN** only literal yes gives manual consent; only literal reject creates pair rejection; active profiles give separate bounded authority; conflicting selections issue no PUT and pending choices remain inspectable.

### Requirement: Pending proposals and file refresh

Every run SHALL read valid approvals, verify or apply eligible corrections, remove confirmed proposals and discover new candidates. It SHALL retain stable pending keys without duplicate entries. Pending probable matches SHALL exclude the related new source import, while unrelated operations continue through existing gates. A valid `decision: reject` SHALL persist a rejected source-target pair, its current evidence binding and reason in private state. It SHALL not delete or modify that activity or reject the source event itself. Keep a compact visible rejected record. A recognized reference still claiming this source SHALL keep the discrepancy visible and held with a required action to inspect or repair that reference; rejection SHALL NOT silently classify it as consistent. Reject requires a complete fresh source and current target association binding. Blocked proposals may be rejected only when that binding is valid; unavailable sources or missing targets suspend choices without granting release. A complete current destination listing that proves an already-rejected target absent SHALL suspend that pair without restoring its candidate hold; retain all other identity and safety guards. An unknown or incomplete listing SHALL still hold. Retain rejection while either endpoint is absent; prune only after a confirmed accepted identity resolves the event, retaining journal recovery and its observed resolution. Changes to association-relevant source evidence or target account, owner, type, security, date, quantity, price or reference, mapping or identity occupancy SHALL invalidate rejection and rediscover a blank manual candidate. Profile, TZ, policy-version, fee, tags, notes and unrelated report changes alone SHALL NOT invalidate rejection. A newly invalidated rejection SHALL receive no automatic authority until its blank decision has been published for a full prior cycle. Unrelated report acquisition changes SHALL not invalidate it. A missing or inactive target SHALL retain a visible hold rather than count as rejection. Source absence SHALL suspend the decision without importing from cached data. Deleting a pending file entry SHALL NOT authorize import: rediscovery SHALL create a blank proposal.

After a selected correction is confirmed, all alternatives for that same source event SHALL leave the pending review. No alternative destination SHALL be modified. Verified manual correction of the selected event to the expected reference and values SHALL also satisfy a proposal without PUT.

If every former candidate now demonstrably belongs to another identified source event, remove those alternatives and release the related import hold. Also release the candidate hold when every current candidate has a valid explicit rejection and no new candidate exists. Carry the rejected pair IDs through ordinary manual/proximity matching so those same pairs do not immediately suppress the event again. Exclude a target from a summed-fill match when any constituent source event validly rejected that target. Do not remove the target from other events' indexes. Rejection SHALL NOT bypass an existing recognized source identity, conflicting reference, unresolved request, corporate-action hold, holdings guard or exact import acceptance. Require fresh, valid ownership/reference evidence for every former candidate. Rebuild candidate and identity indexes, discover any new eligible candidates, then run ordinary import selection. Release SHALL NOT promise an import or bypass its existing gates. A candidate assigned to A SHALL no longer hold a distinct event B solely because B previously matched it. If any candidate remains eligible, retain its pending hold. Disappearance, deactivation, malformed references, unreadable or unsupported destination state SHALL NOT count as assignment to another event. Retain a visible non-actionable proposal in those cases; do not authorize replacement creation.

A changed source event, proposed replacement, destination activity, account/owner, tags, notes, mapping or identity occupancy SHALL invalidate approval. The connector SHALL refresh the displayed proposal, clear `decision` and state the change. Changed report acquisition times, unrelated report rows or window endpoints alone SHALL NOT invalidate unchanged event evidence.

If a previously reviewed event is absent from the current report, its proposal SHALL remain with `source unavailable`. No correction SHALL use cached source data. A still-valid yes SHALL remain suspended until the event returns; changed event values on return SHALL clear it.

### Requirement: Exact replacement and reference preservation

A manually approved financial update SHALL replace the displayed activity fields with the validated current IBKR conversion. A profile-authorized financial update SHALL replace only fields allowed by activity-reconciliation. A reference-only update SHALL replace only the connector comment and preserve every other field. The full proposed comment SHALL be visible before approval. Keep the destination activity ID, destination account, owner and tags. Do not delete or create an activity for a correction. Preserve non-reference user text and all other destination fields outside the explicitly approved changes. Dates/scaling/fee clamps SHALL use the normal import conversion; diagnostic tolerance SHALL grant no write authority.

Define proposed numbers from the exact JSON payload that the current conversion and qualified serializer will send. Show that value as plain-decimal text without additional report rounding. Parse destination response bytes as exact decimals in live and simulated review. Compare numeric values exactly: `1`, `1.0` and `1e0` are equal; financial tolerances SHALL NOT apply. Do not reconstruct destination evidence from already decoded floats. Refuse non-finite values, transport overflow/underflow or loss of any preserved numeric value. A repeating source quotient is represented by the existing conversion's transmitted value, not by an invented exact rational payload.

Compare dates as full UTC instants. Equivalent offsets and fractional-second spellings are equal. A different time on the same UTC day remains a difference. Proposed trade times and dividend midnight SHALL follow existing conversion. UTC calendar dates SHALL control baseline manual proximity; active profile eligibility SHALL use the configured local calendar under activity-reconciliation. Missing timezone evidence or unsupported precision SHALL make exact correction non-actionable.

The canonical v2 reference SHALL occupy the first comment line. If user text exists, append one blank line and that preserved text. Recognized historical references SHALL be removed only when the entire comment is exactly the proven legacy `IBKR#<tradeID>` or `dividend#<key>#<date>` marker. Validate the identifier/key/date against the source and existing supported format; exclude reserved versioned forms from the legacy trade grammar. For example, whole-comment `IBKR#12345` can be upgraded when trade 12345 is proven; `IBKR#12345\n\nMy note` is not a supported legacy reference position and SHALL remain non-actionable rather than be guessed. Canonical v2 supports either the whole comment or the first line followed by exactly one blank separator line and preserved notes. Legacy aggregates that require splitting or merging remain excluded. Several activities sharing a legacy dividend alias can migrate separately only when activity-reconciliation proves mutually unique one-to-one pairs. Text that merely mentions a reference SHALL remain user text. Ambiguous, multiple or malformed reserved references SHALL be refused, not guessed. No comment truncation SHALL be allowed. If API trimming, length or encoding prevents preserving the proposed comment, keep the proposal non-actionable with the reason.

All readers SHALL extract the reference from that first line without treating user text as identity. The original whole-comment v2 forms and legacy readers SHALL remain compatible. Unknown reserved versions and invalid identity segments SHALL still stop before writes. Identity comparison SHALL use the extracted marker, not the full notes-bearing comment. This behavior SHALL remain available when review is later disabled.

### Requirement: Verified correction and dependent import state

Before each dispatch, fresh unredacted destination evidence SHALL match the manually approved or freshly profile-authorized source/target context and unchanged reference occupancy. Require a complete source event in the current report and current destination ownership. The request SHALL include only fields accepted by the qualified update API. No raw GET response SHALL be sent as a PUT. Existing authentication, host validation, redirect rejection and credential protection SHALL apply.

Before the request, durably record its intent, full before/after evidence and manual or profile authority in the journal. Profile authority SHALL include the selected profile, policy version and exact eligibility inputs. Match tolerances SHALL NOT weaken expected-after or preserved-field verification. After the request, readback SHALL prove every approved value and every preserved destination field. A successful status alone SHALL NOT confirm completion. Changes to numeric values or UTC instants, changed owner/account, tags, unsupported profile effects or financial differences SHALL fail verification. Equivalent numeric and timestamp representations defined above SHALL NOT fail verification. Comments and preserved note text SHALL remain exact; trimming is not an equivalent representation. Only confirmed corrections SHALL affect real holdings/identity state. Rebuild that state before ordinary selection and sales checks; replacement of a BUY SHALL NOT add its full quantity a second time.

A known or uncertain correction failure SHALL stop later financial writes for the same account, including imports, cash and platform updates. Earlier confirmed corrections SHALL remain explicit. Later accounts SHALL continue if their own evidence and files remain valid. Ordinary import failures outside this correction path SHALL retain existing independent-cash behavior. Pending proposals alone SHALL warn without failing the account. Those requiring intervention SHALL join the repeated consolidated notification under connector-runtime. Manual approvals and automatic work deferred solely by the qualified execution limit SHALL not request another approval. Automatic work SHALL be freshly re-evaluated next run, never treated as retained user consent. Correction failures SHALL fail the account and enter the existing single Failure summary without financial details.

Manual, automatic and comment-only correction PUTs SHALL share one budget and SHALL be sequential. Each request SHALL complete exact readback before dispatching the next. Activation qualification SHALL establish a finite per-run correction limit and any minimum inter-request delay for the exact destination image, including market-data/background effects. Record the qualified limits in the shipped configuration and operator guidance; do not invent a safe production default from mocks. Stop at the qualified limit without failing the account, preserve unchanged approvals and proposals for the next run, and retain their related import holds. No interactive prompt or separate bulk command SHALL replace normal-run processing.

### Requirement: Durable files and recovery evidence

The operator file, internal evidence state and journal SHALL be private, versioned keyed YAML in the configured persistent directory. Derive `.state.yaml`, journal and companion lock paths from the review filename. Retain complete pending evidence and rejected-pair bindings in internal state; retain full recovery evidence in the existing journal. Bind the compact document generation, keys, revisions and decisions to that state. Exclude credentials. Journal each proposal's complete preimage, expected replacement, input bindings, request state and verified result. The journal SHALL be recovery evidence only. Write new authority-bearing entries as journal version 2; continue reading version 1 and its unresolved requests. Old images SHALL explicitly refuse version 2. Review-schema migration SHALL preserve journal-bound keys and revisions as immutable aliases. Record a deterministic legacy-key to execution-path-qualified-key map in state; v1/v2 journal recovery resolves through it without rewriting journal evidence. Ghostfolio references SHALL remain the accepted-identity authority. Rejected-pair state SHALL only remove explicitly rejected associations from matching; it SHALL NOT invent accepted identities or correspondence records.

Use exclusive runtime locking and atomic, synced file replacement. Persist internal evidence before its compact view. Retain current and previous generation bindings in state. Refuse dispatch on mismatched generations. If the view matches the retained previous generation, recover unchanged key/revision decisions, clear changed ones, republish and revalidate before dispatch. Unknown mismatches preserve both files and stop. Provide `python identity_migration.py rebuild-review --inputs INPUTS --review REVIEW`, an offline simulation-only state rebuild using the existing saved-input manifest contract and no HTTP: first retain the surviving files, preserve every journal and its bound keys/revisions, clear all approvals, create no rejection and explicitly disclose lost rejection history. Rebuild SHALL NOT resolve uncertainty. Mark every rebuilt candidate as profile-ineligible until a subsequent live non-rebuild run has published its blank decision; no profile PUT may occur in that publication cycle. A later run must freshly validate eligibility. A missing or corrupted existing state SHALL stop before financial writes, not reset decisions. Validate all companions against broker, mapping and evidence paths at every output boundary. File paths SHALL reject symlinks, collisions with broker/mapping/evidence inputs and unsafe existing permissions. Concurrent runs sharing the same review SHALL not dispatch overlapping corrections. Detect operator edits before dispatch and before publication; do not overwrite edits or reuse an approval changed during the run. If persistence fails after a possible PUT, retain uncertainty rather than forgetting intent. If a review is globally unreadable or cannot be locked, all accounts using it SHALL stop before financial writes. File-level syntax/schema errors or an unbound unknown proposal SHALL stop all accounts sharing that file; a valid keyed proposal with a non-yes decision SHALL be skipped, except for the explicitly bound reject transition defined above. Operators SHALL edit the review between runs. Advisory locks and byte comparisons detect cooperating writers and observed changes, but cannot prevent an arbitrary editor from racing the final check and replacement. Do not claim atomic compare-and-swap against uncooperative editors. If a concurrent edit is detected, preserve the operator file and pending intent, stop affected dispatch, and report ERROR.

Removing a confirmed proposal SHALL follow durable success recording. If the process stops between these steps, the next run SHALL finish local cleanup without another PUT. The journal SHALL support offline inspection and an exact reverse payload for an unchanged corrected row. Reversal SHALL require separate explicit authority and fresh checks; it SHALL never run automatically. Reverting software SHALL NOT be described as restoring financial data.

### Requirement: Simulation and activation qualification

It SHALL send no financial POST/PUT/DELETE and create no applied journal result. Valid approvals SHALL remain unconsumed. Stale approvals SHALL be cleared using the same rules as live runs. Simulated correction effects SHALL remain isolated from real state. Simulation may display that an unresolved journal now matches expected-after, but SHALL NOT resolve that journal, consume its yes, remove its proposal or release its real account fence. A later live run SHALL revalidate and record observed completion without another PUT.

README SHALL link directly to the activity-review guide. That guide SHALL document the ENV opt-in, persistent-volume permissions, YAML example, literal yes/reject decisions, profile limits, import holds, durable false-match rejection, stale/unavailable status, logs, recovery journal and disabling procedure. Activation SHALL require exact-image isolated qualification of full updates, notes and tags, profile/background effects, duplicate references, restart recovery and no repeat writes. Existing empty/golden release acceptance remains required under its own authority; no new mandatory duration gate is introduced. Source inspection and mocks SHALL NOT be presented as image qualification. A failed preservation case SHALL keep affected corrections unavailable.

### Requirement: Safe review instructions

Each review report requiring user intervention SHALL identify ACTIVITY_REVIEW_FILE and its actual configured container path. Name the generated section and proposal key where available, reason, held scope and safe action. Count unique held source events separately from candidates/proposals. Group repeated reasons without losing affected keys or distinct execution paths. Do not invent a Docker host path or inspect the Docker socket. User documentation SHALL show volume-mapping resolution.

For eligible unapproved normal-run proposals, instruct the user to read current/proposed values and execution path, then edit only decision between runs if the correction is intended. State that only lowercase literal yes approves that exact eligible proposal. Never recommend bulk approval. Blocked, source-unavailable, conflicting or unqualified proposals SHALL name required proof and state that yes cannot make them executable. Historical-maintenance proposals SHALL point to documented preparation and separate operation authorization; normal sync cannot execute them. Uncertain requests SHALL point to preserved journal/readback evidence and prohibit resend, journal deletion or journal edits as release instructions. False matches SHALL offer the bound reject choice and explain that all-rejected events without a recognized reference still claiming them can resume ordinary import, without granting cleanup authority.

Manually approved or profile-authorized work awaiting the qualified per-run limit SHALL report remaining automatic work and its hold. Do not request approval again or force reruns. Simulation SHALL explain that approval executes no financial write in that cycle. Instructions SHALL explain profile authority separately from manual consent. Presentation alone SHALL NOT change qualification, recovery, locking, financial effects or exits. Required actions SHALL join the one per-run notification; keys, paths and financial comparisons remain only in private logs/files.

Baseline: docs/activity-review.md documents two sections and execution paths. The production warning names only the internal path and held-event count.
